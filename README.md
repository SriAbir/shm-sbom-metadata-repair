# SHM: Semantic Harmonization Method for Repairing Incomplete SBOM Metadata

This repository contains the replication package for the paper **“SHM: Semantic Harmonization Method for Repairing Incomplete SBOM Metadata.”**

SHM is a post-generation repair method for incomplete CycloneDX Software Bills of Materials (SBOMs). It identifies repair-eligible components, retrieves exact-version metadata from package-ecosystem sources, generates field-level repair candidates, and applies field-specific static and semantic checks before a repair is accepted.

The public study evaluates SHM on **29 CycloneDX SBOMs** generated by **Syft** and **cdxgen** for **15 open-source projects** from the **npm, PyPI, and Maven** ecosystems. The repository also contains the manually curated ground-truth dataset used to evaluate repair correctness.

## Main Data and Artifacts

### `sboms_raw/`

Contains the original CycloneDX SBOMs used in the main study before SHM repair.

- `sboms_raw/syft/` — SBOMs generated with Syft.
- `sboms_raw/cdxgen/` — SBOMs generated with cdxgen.

The study contains 29 valid SBOMs. One cdxgen generation failed for the Apache Maven project and was retained as a generation failure rather than manually corrected.

### `data/component_metadata_raw.csv`

Common component-level representation extracted from the raw CycloneDX SBOMs. Each row represents a component occurrence in a generated SBOM and retains the associated project, ecosystem, generator, and component metadata.

This file is the main input for the completeness and repair analyses.

### `data/component_repair_candidates.csv`

Contains the field-level repair candidates generated by SHM for missing metadata.

The repair targets are:

- license
- supplier
- repository URL
- hash values
- distribution URL

### `data/component_evidence_summary.csv`

Summarizes metadata retrieved from ecosystem-specific sources for eligible components.

### `evidence_store/registry_evidence_raw.jsonl`

Stores the raw registry evidence retained during metadata retrieval. This file supports provenance and traceability of the generated repair candidates.

### `data/component_repair_provenance.csv`

Contains provenance information associated with generated repair candidates, including the supporting metadata source and component identity information.

### `data/static_validation_*.csv`

Contains outputs of the deterministic/static validation stage, including field-level validation summaries.

### `data/full_semantic_rule_*.csv`

Contains outputs of the field-specific semantic screening stage and the resulting repair decisions.

### `data/ground_truth_sample_500.xlsx`

The manually curated ground-truth dataset used for repair correctness evaluation.

The sample contains **500 unique SBOM component entries**, selected across npm, PyPI, and Maven. The annotation process was performed independently of SHM's proposed repair values.

### `data/ground_truth_comparison_results/`

Contains the detailed outputs produced by comparing SHM repairs with the manually established ground truth. These files support the reported repair precision, proposal coverage, and repair recall results.

Important outputs include files reporting:

- field-level precision;
- proposal coverage;
- repair recall;
- accepted-repair correctness;
- verified cases for which SHM produced no proposal; and
- diagnostic comparisons by metadata field.

### `data/final_completeness_results/`

Contains the completeness measurements after applying only SHM repairs that received the final semantic `accept` decision.

These outputs support the reported before/after completeness and missing-value recovery results.

### `data/repositories.csv` and `data/repository_commits.csv`

Describe the open-source repositories used in the study and the fixed revisions analyzed for reproducibility.

### `data/tool_versions.csv`

Records the versions of the principal tools used in the study environment.

## Scripts

The scripts are organized according to the study workflow.

| Script | Purpose |
|---|---|
| `clone_repositories.py` | Clones the selected open-source projects used in the study. |
| `record_tool_versions.py` | Records versions of the SBOM-generation and analysis tools. |
| `generate_raw_sboms.py` | Generates CycloneDX SBOMs using Syft and cdxgen. |
| `validate_sboms.py` | Checks generated SBOM files before analysis. |
| `extract_sbom_fields.py` | Extracts component-level metadata from CycloneDX SBOMs into a common tabular representation. |
| `compute_missing_field_statistics.py` | Computes baseline field-level metadata completeness used for RQ1. |
| `classify_repair_eligibility.py` | Determines which component occurrences can proceed to automatic registry-based repair. |
| `retrieve_registry_evidence.py` | Retrieves exact-version metadata from npm, PyPI, and Maven sources and records supporting evidence. |
| `generate_repair_proposals.py` | Creates field-level repair candidates for missing CycloneDX metadata. |
| `validate_repair_proposals_static.py` | Applies deterministic/static validation rules to generated repair candidates. |
| `validate_semantic_rules.py` | Applies field-specific semantic checks and assigns final repair decisions. |
| `evaluate_ground_truth.py` | Compares SHM repairs with the manually curated ground truth and computes repair precision, proposal coverage, and repair recall. |
| `evaluate_final_completeness.py` | Applies accepted repairs and computes final metadata completeness and missing-value recovery. |
| `generate_rq1_figure.py` | Generates the RQ1 metadata-coverage visualization. |
| `generate_shm_validation_figure.py` | Generates the SHM candidate/static/semantic validation-flow figure. |
| `industrial_repair_eligibility.py` | Applies the repair-eligibility logic used for the industrial case-study components. |
| `industrial_cargo_extension.py` | Provides the Cargo/crates.io metadata-retrieval extension used in the industrial case study. |

## Environment and Requirements

Python dependencies are listed in:

```text
requirements.txt
```

Install them with:

```bash
pip install -r requirements.txt
```

To regenerate the original SBOMs, **Syft** and **cdxgen** must also be installed and available on the system `PATH`. The versions used in the study are recorded in:

```text
data/tool_versions.csv
```

Internet access is required for operations that clone repositories or retrieve current package-registry metadata.

Because package-registry metadata can change over time, the replication package also includes the metadata and raw evidence retrieved during the study. These retained artifacts should be used when reproducing the reported results exactly.

## Reproducing the Study

Two replication paths are possible.

### A. Reproduce the analysis from the supplied SBOMs

This is the recommended path for reproducing the reported study results because it uses the original SBOMs included in `sboms_raw/`.

Run the scripts from the repository root in the following order:

```bash
python scripts/validate_sboms.py
python scripts/extract_sbom_fields.py
python scripts/compute_missing_field_statistics.py
python scripts/classify_repair_eligibility.py
python scripts/retrieve_registry_evidence.py
python scripts/generate_repair_proposals.py
python scripts/validate_repair_proposals_static.py
python scripts/validate_semantic_rules.py
python scripts/evaluate_ground_truth.py
python scripts/evaluate_final_completeness.py
```



### B. Regenerate the SBOMs from the selected projects

To reproduce the study from the source repositories:

```bash
python scripts/clone_repositories.py
python scripts/record_tool_versions.py
python scripts/generate_raw_sboms.py
```

The remaining analysis can then be run using the sequence shown above.

The source revisions used in the original study are recorded in:

```text
data/repository_commits.csv
```

Regenerated SBOMs may vary if different versions of Syft, cdxgen, package managers, or build environments are used. For comparison with the paper results, the SBOMs distributed in `sboms_raw/` should therefore be treated as the study inputs.

### RQ3 — Industrial case study

The paper also evaluates SHM on previously unseen CycloneDX SBOMs from an industrial partner. The industrial setting required an additional Cargo/crates.io metadata-resolution layer while retaining the same field-specific repair principles.

The public repository includes the generic implementation of this extension:

```text
scripts/industrial_repair_eligibility.py
scripts/industrial_cargo_extension.py
```

#### Industrial data availability

The original industrial SBOMs and the practitioner-validation workbook are **not included in this public replication package** because they contain company-provided information subject to confidentiality restrictions.

To protect the industrial partner:

- the original company SBOMs are not redistributed;
- the practitioner validation file is not released;
- company-identifying information is not included in the public artifact; and
- the released industrial scripts use generic naming and expose only the method used to extend SHM to the additional ecosystem.

Consequently, the industrial case-study results reported in the paper cannot be fully regenerated from the public artifact alone. The open-source evaluation underlying RQ1 and RQ2 is provided independently and is reproducible from the released data and scripts.

## Ground-Truth Evaluation

The ground-truth evaluation is based on:

```text
data/ground_truth_sample_500.xlsx
```

The evaluation script:

```bash
python scripts/evaluate_ground_truth.py
```

compares the final SHM decisions against verified missing-field values and produces the outputs under:

```text
data/ground_truth_comparison_results/
```

The reported metrics distinguish three aspects of repair behavior:

- **Repair precision:** proportion of evaluated accepted repairs that are correct.
- **Proposal coverage:** proportion of verifiable missing fields for which SHM generates a repair proposal.
- **Repair recall:** proportion of verifiable missing fields that SHM ultimately repairs correctly.

These metrics should not be interpreted interchangeably: a method can produce highly precise accepted repairs while intentionally abstaining from cases where the available evidence is insufficient.

## Notes on Reproducibility

1. **Registry evidence is version-sensitive.** Public package metadata may change after the original experiment. The retained evidence in `evidence_store/` and `data/` corresponds to the study run.

2. **SHM preserves existing non-empty SBOM values.** The repair process targets missing metadata rather than replacing already populated fields.

3. **Version and PURL are used primarily for component identification.** The automatic repair evaluation focuses on license, supplier, repository URL, hash values, and distribution URL.

4. **Only accepted repairs are applied automatically.** Candidates routed to caution, manual review, or rejection are not written automatically to the repaired SBOM representation.

5. **Industrial data are intentionally excluded.** Their absence is a confidentiality constraint rather than a missing artifact.
